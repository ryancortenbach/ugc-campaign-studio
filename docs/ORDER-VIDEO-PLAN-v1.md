# Local package video assignment plans

This extends PR4 against post-judging. Main remains separate from these post-demo changes. No app or live account was activated.

The current pipeline has one storyboard per order. The new backend records an explicit video count, source note and slot-to-storyboard assignments without changing the original order storyboard, payment snapshot, render IDs, finals or drafts. It never generates storyboards, renders, uploads, sends or claims buyer delivery. This is planning storage, not full package fulfillment.

GET /api/whop/orders/:id/video-plan returns an unsaved revision-zero suggestion until the operator saves. The original storyboard is suggested for slot one, but videoCount stays null. A dated listed package count is a separate suggestion. scopeVerified remains false. The operator must explicitly provide an integer count from one to fifty and a nonempty source note. A saved note is not external contract verification.

POST to the same route requires expectedRevision, videoCount, scopeNote and assignments. Each assignment has a unique slot and storyboardId. Slots must fall within the recorded count and all referenced boards/ancestors must exist. Two revisions from the same storyboard family cannot count as separate videos. Missing, cyclic or excessively deep ancestry is rejected. Storyboards reserved by another order, including its legacy order storyboard family, cannot be reused. Family ownership reservations persist even if a later plan removes a slot. There is no transfer/unreserve operation.

A SQLite immediate transaction validates the expected revision, reserves roots and saves both the new current plan and an immutable history row. Failure rolls back all changes. GET /api/whop/orders/:id/video-plan/versions/:revision retrieves the saved plan. The version payload retains its saved count, source note and assignments; the separate suggestedScope comes from the order's currently saved payment snapshot. Existing order, storyboard and payment data remain unchanged.

Three local tables are initialized when the module is loaded with a store: order_video_plans, order_video_plan_versions and order_video_owners. GETs do not create plan records. No actual app store was opened or migrated by this worker. Tests use memory or temporary-file SQLite stores. The metadata-only POST is permitted under the existing no-spend guard and invokes no provider or delivery method.

Current limits: no UI, no automatic package rendering, no per-slot final/storage records, no buyer delivery tracking. The separate coverage endpoint still describes the legacy one-storyboard flow and does not consume this inventory yet. Ownership is enforced for saves through this module; unrelated legacy writers are not globally rewritten. Unrelated missing/cyclic/deep legacy ancestry is reported as unresolvedLegacyOrderCount and does not block all other orders. Ownership checks cover current saved references and persistent reservations; missing history is not reconstructed. Invalid ancestry on a candidate assignment is rejected. No externally verified scope, payment refresh or human review execution is implied.
